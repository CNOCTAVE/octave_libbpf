octave_libbpf文档
欢迎广大开发者将此文档翻译为其他语言。

octave_libbpf 是 GNU Octave 的 libbpf 封装。它把 eBPF 的参考用户态库 libbpf 完整地暴露给 Octave， 并在其之上用纯 m 代码实现了一整套 eBPF 工具链：指令编码器与汇编器、BTF 类型编码器、以及 ELF64/BPF 目标文件写出器。 因此你可以在 Octave 命令行里直接编写、汇编、加载、挂载、检查并驱动 eBPF 程序，既不需要 clang，也不需要写一行 C 代码。 此外，octave_libbpf 还可以直接运行由其他工具生成的 eBPF 程序。

功能特性
一、完整的 libbpf 绑定

src/libbpf_wrap.cc 编译出的 libbpf_wrap.oct 提供 182 个子命令，覆盖 libbpf 的全部主要接口： bpf_object（打开、加载、固定、遍历）、bpf_program 及其全部 attach 家族（kprobe、kprobe_multi、uprobe、 uprobe_multi、tracepoint、raw_tracepoint、fentry/fexit、lsm、cgroup、netns、xdp、tcx、netkit、sockmap、 freplace、netfilter、iter、usdt、perf_event、ksyscall）、bpf_map（创建、增删改查、批量、固定、信息）、 bpf_link、ring buffer、perf buffer、BTF（解析、遍历、加载、反汇编）以及低层 bpf_*() 系统调用封装。

二、在 Octave 中编写 eBPF 程序

bpf.Builder、bpf.Asm、bpf.Insn 覆盖 eBPF 指令集的全部助记符（ALU/ALU64、跳转、内存读写、 原子操作、字节序转换、伪指令加载等），支持符号标号跳转与 map 重定位。bpf.BtfBuilder 负责生成 map 的 BTF 描述， bpf.Elf 负责生成 ELF64/BPF 目标文件，最后交给 libbpf 校验、加载并挂载，全部过程都在 Octave 内完成。

三、面向对象的对象模型

bpf.Object、bpf.Program、bpf.Map、bpf.Link、bpf.RingBuf、bpf.PerfBuf、bpf.BTF 让常用流程变得简洁： 打开、加载、挂载、读写 map、收取 ring buffer 事件都可以用一行代码完成，对象的生命周期由 Octave 的 handle 类自动管理。

四、同样支持 clang 编译的对象

bpf.Object.from_file() 可以加载任何 eBPF ELF 目标文件，无论是 octave_libbpf 自己生成的， 还是用 clang -target bpf 生成的。传统 libbpf 工作流可以原封不动地用 Octave 驱动。

软件源安装

octave_libbpf 发布到 Octave Forge 软件源之后，可以通过 Octave 软件源安装。

通过Octave软件源安装octave_libbpf，代码如下：

>> pkg install -forge octave_libbpf

注意：截至 0.1.0 版本，octave_libbpf 尚未进入 Octave Forge 软件源， 请使用下面的“在线安装”或“源码安装”方式。
在线安装

octave_libbpf 可以在线安装，也可以用已经打包好的 tar.gz 安装包本地安装。

在线安装octave_libbpf，代码如下：

>> pkg install 'https://github.com/CNOCTAVE/octave_libbpf/releases/download/0.1.0/octave_libbpf-0.1.0.tar.gz'

本地安装octave_libbpf-0.1.0.tar.gz，代码如下：

>> pkg install octave_libbpf-0.1.0.tar.gz

安装过程中会在 src 目录中自动探测 libbpf 的头文件与共享库，并编译 oct 文件。
源码安装

如果希望直接从源码树构建，可以在包目录里使用 make。

构建 oct 文件：

$ make -C octave_libbpf/src

打包、安装并运行测试：

$ make dist # 生成 ../octave_libbpf-0.1.0.tar.gz

$ make install # 对该 tar 包执行 pkg install

$ make test # 安装并执行 pkg test octave_libbpf

如果不想安装，也可以直接把源码树加入搜索路径：

>> addpath ('octave_libbpf/src');

>> addpath ('octave_libbpf/inst');

如何使用
在安装后，加载octave_libbpf即可使用，代码如下：

>> pkg load octave_libbpf

查看运行环境：

>> bpf.version () % libbpf 版本，例如 major = 1, minor = 6

>> bpf.num_cpus () % possible CPU 数量，用于 per-CPU map

>> bpf.have_bpf () % 当前进程是否可以加载 eBPF 程序与 map

>> numel (bpf.commands ()) % 底层 libbpf_wrap 支持的子命令数量

运行自带演示与帮助：

>> demo_octave_libbpf

>> help octave_libbpf

权限说明：

加载 eBPF 程序需要 CAP_BPF（5.8 之前的内核需要 CAP_SYS_ADMIN），因此通常需要以 root 运行， 或者给 octave 授予相应能力。汇编、BTF/ELF 生成、类型表查询等纯用户态功能不需要任何特权。 对于 5.11 之前的内核，创建较大的 map 之前还需要调用 bpf.memlock() 提高 RLIMIT_MEMLOCK。

依赖库
Fedora / RHEL：

$ sudo dnf install libbpf-devel

Debian / Ubuntu：

$ sudo apt install libbpf1-devel

当系统没有安装 libbpf-devel 时，包会使用自带在 src/vendor/bpf 中的公共 libbpf 头文件进行编译， 因此只需要运行时库即可。发行版常常只安装 libbpf.so.1 而没有 libbpf.so 或 libbpf.pc， 构建系统会自动回退到 -l:libbpf.so.1，并允许用 LIBBPF_ROOT / LIBBPF_LIBS 覆盖探测结果。

另外还需要 Linux 内核提供 eBPF 支持（4.x 以上，建议 5.8 以上以获得 CAP_BPF 与完整的 BTF、ring buffer、kprobe_multi 等特性）。

在其他的Linux发行版上的命令有所不同。欢迎广大开发者补充。
用Octave编写eBPF程序

下面这个程序统计 do_sys_openat2() 的调用次数，并把计数保存在一个 array map 里。 整段程序由 Linux 内核校验后真正运行，没有任何 C 代码参与。

pkg load octave_libbpf

R = bpf.regs ();
b = bpf.Builder ('GPL');
counts = b.map ('counts', 'array', 'u32', 'u64', 8);

p = b.program ('kprobe/do_sys_openat2', 'count_open');
p.st_w (R.R10, -4, 0);                              % u32 key = 0
p.ld_map_fd (R.R1, 'counts');                       % r1 = &counts（重定位）
p.mov64_reg (R.R2, R.R10);                          % r2 = &key
p.add64_imm (R.R2, -4);
p.call (bpf.helper ('map_lookup_elem'));
p.jeq_imm (R.R0, 0, 'done');                        % if (!value) goto done
p.mov64_imm (R.R1, 1);
p.atomic_dw (R.R0, R.R1, 0, bpf.atomic_op ('add'));  % __sync_fetch_and_add
p.label ('done');
p.mov64_imm (R.R0, 0);
p.exit ();

obj = b.build ();        % 汇编 + BTF + ELF64/BPF 镜像
obj.load ();             % 交给 libbpf 校验并加载
obj.attach_all ();       % 挂载 kprobe

obj.find_map ('counts').lookup (0)
程序段名决定程序类型。

bpf.Builder 根据 program() 的段名（SEC）自动推断程序类型与 attach 类型， 例如 kprobe/、kretprobe/、raw_tp/、tracepoint/、fentry/、fexit/、lsm/、iter/、xdp、socket、cgroup/ 等， 与 clang 编译 eBPF 程序时的规则完全一致。bpf.Program.attach() 也会按段名自动选择挂载方式。

函数用法

octave_libbpf 提供以下底层可加载函数（libbpf_wrap.oct，182 个子命令）和 Octave 封装函数， 涵盖 eBPF 程序编写、对象加载与挂载、map 读写、环形缓冲区、BTF 类型信息等能力。

一、编写 eBPF 程序（纯 m 代码工具链）
bpf.Builder

Function File: b = bpf.Builder ()

Function File: b = bpf.Builder (LICENSE)

创建 eBPF 对象构造器，LICENSE 默认为 'GPL'。一个 Builder 收集本次对象的全部 map 与 program， 并负责把它们变成 libbpf 可以加载的 ELF64/BPF 镜像。

m = b.map (NAME, TYPE, KEYTYPE, VALUETYPE, MAXENTRIES [, OPTS])　声明一个 map。 TYPE 可以是名字或编号（'array'、'hash'、'ringbuf'、'percpu_hash'、'lru_hash'、'prog_array' 等）。 KEYTYPE / VALUETYPE 支持 'u8' 'u16' 'u32' 'u64' 's8' 's16' 's32' 's64' 'char' 'bool' 'ptr'， 也可以给出一个字节数表示不透明类型，或用 struct('btf', ID) 引用已经加入 bpf.BtfBuilder 的类型。 OPTS 可以包含 map_flags、pinning、numa_node、map_extra、key_size、value_size 等字段。

p = b.program (SECTION, NAME)　声明一个程序并返回它的 bpf.Asm 汇编器； SECTION 即 SEC 段名，决定程序类型。p = b.prog (...) 是它的简写。

img = b.elf ()　返回生成的 ELF 镜像（uint8 行向量）。

o = b.build ()　等价于 bpf.Object.from_mem (b.elf ())。

b.write (PATH)　把 ELF 镜像写入文件，可以交给 bpftool、llvm-objdump 等工具检查。

names = b.map_names ()　names = b.program_names ()　m = b.find_map (NAME)　s = b.source ()

bpf.Asm

Class: a = bpf.Asm ()

eBPF 汇编器。它收集指令、解析符号标号、记录 map 重定位。全部 125 个指令助记符都可以作为方法调用， 参数与 bpf.Insn 完全一致；跳转类助记符的最后一个参数可以写成字符串形式的标号。

a.label (NAME)　在当前指令位置定义标号。

a.jump (NAME)　无条件跳转到标号。

a.ld_map_fd (DST, MAP)　加载 map 的文件描述符，生成 R_BPF_64_64 重定位。

a.ld_map_value (DST, MAP, OFF)　a.ld_map_idx (DST, MAP)

b = a.bytes ()　N×8 的 uint8 指令流。n = a.count ()　已使用的指令槽数量。

r = a.relocations ()　结构体数组，字段为 slot、sym、kind。

s = a.source ()　可读的汇编清单（cellstr），寄存器显示为 r0…r10。

a.patch (INDEX, BYTES)　替换指定槽位的指令。a.emit (BYTES)　直接追加编码后的字节。

bpf.Insn

Function File: bytes = bpf.Insn (MNEMONIC, ...)

编码一条 eBPF 指令（ld_imm64 为两条），返回 1×8（或 1×16）的 uint8 行向量。

通用形式：bpf.Insn ('raw', CODE, DST, SRC, OFF, IMM)

算术与逻辑：mov/add/sub/mul/div/or/and/lsh/rsh/mod/xor/arsh/neg， 每种都有 64 位与 32 位、imm 与 reg 的组合，例如 mov64_imm、add32_reg。 字节序转换使用 end_le 与 end_be，第二个参数是位宽。

内存访问：ldx_w ldx_h ldx_b ldx_dw、stx_w stx_h stx_b stx_dw、st_w st_h st_b st_dw， 以及传统的 ld_abs_* 与 ld_ind_*。

分支：ja、jeq/jgt/jge/jset/jne/jsgt/jsge/jlt/jle/jslt/jsle 的 _imm 与 _reg 形式， 以及对应的 jmp32_* 形式；call、callx、exit。

原子操作：atomic_w atomic_h atomic_b atomic_dw，最后一个参数是 bpf.atomic_op() 的返回值。

特殊形式：ld_imm64、ld_map_fd、ld_map_value、ld_map_idx、ld_btf_id、ld_func。

bpf.MapDef

Class: m = bpf.MapDef (NAME, TYPE, KEYTYPE, VALUETYPE, MAXENTRIES)

map 的描述对象，通常由 bpf.Builder.map() 创建。属性包括 name、type、type_name、 key、value、max_entries、map_flags、pinning、numa_node、map_extra、key_size、value_size， 以及 is_ringbuf() 与 is_percpu() 两个判定方法。

bpf.BtfBuilder

Class: B = bpf.BtfBuilder ()

BTF（BPF Type Format）编码器，负责生成 ELF 的 .BTF 段。类型编号从 1 开始，0 表示 void。

id = B.add_int (NAME, SIZE, ENCODING)　B.add_ptr (TYPE)　B.add_array (TYPE, NELEMS [, INDEX_TYPE])

id = B.add_struct (NAME, MEMBERS)　B.add_union (NAME, MEMBERS)　B.add_typedef (NAME, TYPE)

id = B.add_const (TYPE)　B.add_volatile (TYPE)　B.add_restrict (TYPE)　B.add_fwd (NAME [, IS_UNION])

id = B.add_enum (NAME, NAMES, VALUES [, SIZE])　B.add_func_proto (RET [, PARAMS])　B.add_func (NAME, PROTO)

id = B.add_var (NAME, TYPE [, LINKAGE])　B.add_datasec (NAME, VARS)　B.add_decl_tag (NAME, TYPE, IDX)

n = B.type_cnt ()　s = B.size_of (ID)　s = B.name_of (ID)　k = B.kind_of (ID)　b = B.bytes ()

常量属性：KIND_INT 等全部 BTF kind、ENC_NONE/ENC_SIGNED/ENC_CHAR/ENC_BOOL、 VAR_STATIC/VAR_GLOBAL_ALLOCATED/VAR_GLOBAL_EXTERN。

bpf.Elf

Class: E = bpf.Elf ()

最小的 ELF64/BPF 重定位目标文件写出器。

idx = E.add_section (NAME, TYPE, FLAGS, ALIGN, DATA)　E.add_relocs (TARGET_IDX, ENTRIES)

E.add_symbol (NAME, VALUE, SIZE, INFO, SHNDX [, OTHER])　b = E.bytes ()

常量属性包括 SHT_*、SHF_*、STB_*、STT_*、R_BPF_*、EM_BPF、ET_REL。

bpf.regs

Function File: R = bpf.regs ()

返回 r0…r10 的寄存器编号结构体：R.R0 … R.R10，另有 R.FP（10）与 R.RET（0）。

bpf.helper

Function File: id = bpf.helper (NAME)

按名字查询 eBPF helper 函数编号，'map_lookup_elem' 与 'bpf_map_lookup_elem' 都可以。 表由 libbpf 的 bpf_helper_defs.h 生成，共 211 个 helper。也可以直接传入编号。

bpf.atomic_op

Function File: op = bpf.atomic_op (NAME [, FETCH])

返回原子指令的立即数：'add' 'or' 'and' 'xor' 默认带 BPF_FETCH，'xchg' 与 'cmpxchg' 不带； 第二个参数可以显式控制是否带 fetch。

三、类型、枚举与字节转换
bpf.map_type / bpf.prog_type / bpf.attach_type / bpf.link_type

Function File: [VALUE, NAME] = bpf.map_type (KEY)　（其余三个规则相同）

按名字或编号解析内核枚举。名字不区分大小写，可以带前缀也可以省略， 例如 'array'、'ARRAY'、'BPF_MAP_TYPE_ARRAY'、2 都解析为 2。编号输入会原样返回，并尽量补全规范名。

bpf.enum_lookup

Function File: [VALUE, NAME] = bpf.enum_lookup (GROUP, KEY [, PREFIX])

上面四个函数的底层实现。GROUP 是 bpf.enum_table() 中的一个字段，例如 'bpf_map_type'、'bpf_prog_type'、 'bpf_attach_type'、'bpf_link_type'、'bpf_cmd'。枚举表由系统头文件 <linux/bpf.h> 解析生成，共 256 个常量。

bpf.bytes2num / bpf.num2bytes

Function File: v = bpf.bytes2num (BYTES [, SIGNED])

Function File: b = bpf.num2bytes (V [, N])

在小端字节向量与整数之间转换，1/2/4/8 字节分别对应 uint8/uint16/uint32/uint64。 这两个函数在 map 读写以及 BTF/ELF 编码中被广泛使用。

四、运行环境与诊断
bpf.version

Function File: v = bpf.version ()

返回结构体 major、minor、string，描述当前链接的 libbpf 版本。

bpf.commands

Function File: c = bpf.commands ()

返回 libbpf_wrap.oct 支持的全部子命令名（已排序的 cellstr），当前为 182 个。

bpf.raw

Function File: [A, B, ...] = bpf.raw (COMMAND, ARG, ...)

直接调用底层 oct 文件的逃生通道，可以访问完整的 libbpf 绑定。指针以 uint64 标量传递， 错误会以 "libbpf: ..." 开头的 Octave 异常抛出。

bpf.probe

Function File: tf = bpf.probe (WHAT, ARG [, ARG2])

探测内核能力：bpf.probe('prog_type', TYPE)、bpf.probe('map_type', TYPE)、 bpf.probe('helper', PROG_TYPE, HELPER)。探测通过尝试加载一个最小程序完成，因此可能需要一点时间。

bpf.have_bpf

Function File: tf = bpf.have_bpf ()

五、底层绑定 libbpf_wrap

oct 文件只暴露一个函数 libbpf_wrap (COMMAND, ARG, ...)，按字符串分发到 182 个处理函数。 约定：句柄是 uint64 标量形式的 C 指针；可选参数以 Octave 标量结构体传入；二进制数据以 uint8 行向量传递； 返回指针的 libbpf 调用会用 libbpf_get_error() 检查并转成 Octave 异常。

主要命令组：object_*（打开、加载、关闭、固定、查找）、program_*（元信息、日志、全部 attach）、 map_*（创建、元素读写、批量、固定、信息）、link_*、ringbuf_*、perfbuf_*、btf_*（解析、遍历、加载、反汇编）， 以及 prog_* / map_* 等底层系统调用封装（bpf_prog_load、bpf_map_create、bpf_obj_get/pin、bpf_prog_attach 等）。

用 bpf.commands() 可以列出全部命令，用 bpf.raw() 可以直接调用它们。

实现原理

octave_libbpf 分成两层：上面是纯 m 代码实现的 eBPF 工具链与对象模型， 下面是 src/libbpf_wrap.cc 编译出的 oct 文件，它把 Octave 值转成 C 值、调用系统 libbpf，再把结果转回 Octave。 C++ 层不做任何策略判断，因此行为与直接用 C 调用 libbpf 完全一致。

一段 Octave 程序如何变成内核里的 eBPF 程序

1. bpf.Asm 用 bpf.Insn 编码每条指令，解析符号标号，并记录 map 引用。

2. bpf.BtfBuilder 编码描述每个 map 的 BTF，也就是 libbpf 1.0 之后要求的现代 map 定义形式： int (*type)[BPF_MAP_TYPE_ARRAY]、int (*max_entries)[8]、__u32 *key、__u64 *value， 再加上每个 map 的 VAR 记录和一条 .maps 的 DATASEC 记录。

3. bpf.Elf 生成 ELF64 小端、EM_BPF（247）的 ET_REL 目标文件：程序段、.maps、license、.BTF、 符号表，以及每个引用 map 的程序段对应的一条 SHT_REL 重定位段。

4. bpf.Object.from_mem 把镜像交给 bpf_object__open_mem()；之后 libbpf 会像处理 clang 生成的 .bpf.o 一样完成校验、map 创建、程序加载与固定。

几个容易出错、但已经处理好的细节

1. BTF_KIND_ARRAY 中未使用的 size/type 字段必须为 0，否则内核会以 "size != 0" 拒绝整个 BTF。

2. BTF_KIND_INT 的 encoding 字里存放的是位宽（nr_bits），而不是字节数。

3. ring buffer 类型的 map 必须省略 key/value 成员，使 key_size 与 value_size 为 0。

4. 写 ELF 程序段时必须按指令顺序展平 N×8 的指令矩阵，不能按列优先。

5. 发行版往往只安装 libbpf.so.1 而没有开发链接，因此构建系统需要回退到 -l:libbpf.so.1； 同时因为 libbpf 只会在公开结构体尾部追加字段，用较新头文件编译的包可以安全运行在较旧的共享库上。

更详细的说明见包内的 doc/design.md。

两个 Octave 语法注意事项

1. 在 cell 或矩阵字面量里，函数名与左括号之间如果写了空格，会被解析成命令语法， 逗号后面的项会变成额外的实参。例如 { fullfile ('/tmp'), 2 } 其实是 1×3 的 cell， 应当写成 {fullfile('/tmp'), 2}。

2. bpf.xxx (ARG).field 这种“包函数调用后紧跟字段访问”的写法 Octave 无法解析， 请先把结果赋给变量。这也是 bpf.map_type() 等函数直接返回数值、而把名字作为第二个输出的原因。

tst_insn.m —— 指令编码

逐条验证 bpf.Insn 的二进制编码，以及 bpf.Asm 的标号解析与重定位记录。这一组用例完全在用户态运行，不需要 eBPF 权限，任何环境都会执行。

用例 1：mov64_imm r1, 1
原始用例（mov64_imm r1, 1） 
b = bpf.Insn ('mov64_imm', 1, 1);
assert (class (b), 'uint8');
assert (size (b), [1, 8]);
assert (b, uint8 ([0xb7, 0x01, 0x00, 0x00, 0x01, 0x00, 0x00, 0x00]));

最基本的 ALU64 立即数传送。opcode 0xb7 由 BPF_ALU64、BPF_MOV、BPF_K 三部分按位或成； 第 2 字节 0x01 的低 4 位是目的寄存器 r1，高 4 位是源寄存器（立即数形式下为 0）； 后 4 字节是小端立即数 1。这里同时确认返回值一定是 1×8 的 uint8 行向量，这是后面拼装整条指令流的基础约定。

用例 2：mov64_reg r2, r10
原始用例（mov64_reg r2, r10） 
b = bpf.Insn ('mov64_reg', 2, 10);
assert (b, uint8 ([0xbf, 0xa2, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00]));

寄存器到寄存器传送，opcode 0xbf（加上 BPF_X 表示源操作数是寄存器）。 第 2 字节 0xa2 的低位是 dst=2、高位是 src=10，说明寄存器编号的打包顺序没有弄反—— 这类看起来"显然"的地方恰恰是编码器最容易写错的地方。

用例 3：mov32_imm 属于 32 位 ALU 类
原始用例（mov32_imm is the 32 bit ALU class） 
b = bpf.Insn ('mov32_imm', 0, 7);
assert (b(1), uint8 (0xb4));

32 位版本使用 0xb4（BPF_ALU 而不是 BPF_ALU64），与 64 位版本相差 3。 这条用例专门盯住"64/32 位判定"这个曾经的缺陷：早期实现把 64 位误判成 32 位， 于是所有 ALU 指令的 opcode 都偏了 3，内核校验器报出一堆莫名其妙的错误。

用例 4：负偏移与负立即数使用补码
原始用例（negative offsets and immediates are two's complement） 
b = bpf.Insn ('st_w', 10, -4, 0);
assert (b, uint8 ([0x62, 0x0a, 0xfc, 0xff, 0x00, 0x00, 0x00, 0x00]));

栈访问 st_w r10, -4, 0：opcode 0x62（BPF_ST｜BPF_MEM｜BPF_W）， 偏移 -4 编码为 0xfc 0xff，即 int16 的小端补码。eBPF 的栈只能通过 r10（帧指针）加负偏移访问，所以负偏移的编码必须完全正确。

用例 5：带负偏移的无条件跳转
原始用例（an unconditional branch with a negative offset） 
b = bpf.Insn ('ja', -3);
assert (b, uint8 ([0x05, 0x00, 0xfd, 0xff, 0x00, 0x00, 0x00, 0x00]));

ja -3 的 opcode 是 0x05，偏移同样是 16 位补码。 向后跳转是循环的基础，这条用例确认反向偏移不会被当成无符号数写坏。

用例 6：exit
原始用例（exit） 
assert (bpf.Insn ('exit'), uint8 ([0x95, 0, 0, 0, 0, 0, 0, 0]));

0x95 是 BPF_JMP｜BPF_EXIT，其余字段全 0。 每个 eBPF 程序都必须以 exit 结束（或者以别的终结指令结束）， 否则内核校验器会直接拒绝整个程序。

用例 7：ld_imm64 占用两个指令槽
原始用例（ld_imm64 occupies two instruction slots） 
b = bpf.Insn ('ld_imm64', 1, 5);
assert (size (b), [1, 16]);
assert (b(1:8), uint8 ([0x18, 0x01, 0x00, 0x00, 0x05, 0x00, 0x00, 0x00]));
assert (b(9:16), uint8 ([0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00]));

64 位立即数加载要占 两条指令（16 字节）：第一条 opcode 0x18 （BPF_LD｜BPF_IMM｜BPF_DW），低 32 位放在第一条的 imm 里，高 32 位放在第二条的 imm 里。 汇编器必须为它记 2 个槽位，否则后面所有标号的偏移都会错位一位。

用例 8：ld_map_fd 使用 BPF_PSEUDO_MAP_FD 源寄存器
原始用例（ld_map_fd uses the BPF_PSEUDO_MAP_FD source register） 
b = bpf.Insn ('ld_map_fd', 1);
assert (b(1:8), uint8 ([0x18, 0x11, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00]));

引用 map 的伪指令：opcode 仍然是 0x18，但把 src_reg 字段写成 BPF_PSEUDO_MAP_FD（值为 1），所以第 2 字节是 0x11（dst=1、src=1）。 libbpf 在加载时会根据重定位把真正的 map 文件描述符填进 imm。

用例 9：超过 32 位的 64 位立即数
原始用例（a 64 bit immediate wider than 32 bits） 
b = bpf.Insn ('ld_imm64', 2, 0x123456789);
assert (b(5:8), uint8 ([0x89, 0x67, 0x45, 0x23]));
assert (b(13:16), uint8 ([0x01, 0x00, 0x00, 0x00]));

0x123456789 的低 32 位 0x23456789 放在第一条 imm， 高 32 位 0x1 放在第二条 imm，两者都是小端。 这条用例保证了 64 位立即数不会被截断——早先的实现曾经把低 32 位整个丢掉， 只留下高 32 位。

用例 10：调用 helper 函数
原始用例（a call to a helper） 
b = bpf.Insn ('call', bpf.helper ('map_lookup_elem'));
assert (b(1), uint8 (0x85));
assert (double (bpf.bytes2num (b(5:8))), bpf.helper ('map_lookup_elem'));

call 的 opcode 是 0x85（BPF_JMP｜BPF_CALL），imm 是 helper 编号。 用例先用 bpf.helper('map_lookup_elem') 取出编号（1）， 再用 bpf.bytes2num 把编码好的 imm 解回来对比， 一次覆盖 helper 表、指令编码、字节还原三条链路。

用例 11：64 位与 32 位条件跳转使用不同的指令类
原始用例（64 bit and 32 bit conditional branches use different classes） 
a = bpf.Insn ('jeq_reg', 1, 2, 5);
c = bpf.Insn ('jmp32_jeq_reg', 1, 2, 5);
assert (a(1), uint8 (0x1d));
assert (c(1), uint8 (0x1e));

jeq_reg 是 0x1d（JMP｜JEQ｜X）， jmp32_jeq_reg 是 0x1e（JMP32｜JEQ｜X），两者只差 1。 比较 64 位与 32 位操作数是两个不同的指令类，混用会让比较结果出错， 而错误往往只在特定数据下才暴露。

用例 12：拒绝未知助记符
原始用例（unknown mnemonics are rejected） 
fail ('bpf.Insn (''not_a_real_instruction'', 1, 2)', 'unknown mnemonic');

非法助记符必须立即报错，而不是静默生成一条垃圾指令。 汇编器越早失败越安全：生成一份"看起来能加载"的错误字节， 通常要在内核校验器里绕一大圈才能定位。

用例 13：helper 表与类型表
原始用例（helper and type tables） 
assert (bpf.helper ('map_lookup_elem'), 1);
assert (bpf.helper ('bpf_map_lookup_elem'), 1);
assert (bpf.map_type ('array'), 2);
assert (bpf.map_type ('BPF_MAP_TYPE_RINGBUF'), 27);
assert (bpf.prog_type ('kprobe'), 2);
assert (bpf.atomic_op ('add'), 1);
assert (bpf.atomic_op ('add', false), 0);
assert (bpf.atomic_op ('cmpxchg'), 240);

检查几张由头文件生成的表：bpf.helper 同时接受带前缀与不带前缀的名字； bpf.map_type 支持短名、全名与编号；bpf.prog_type 按名字查程序类型； bpf.atomic_op 的 fetch 位（add 默认带 BPF_FETCH=1、显式关掉为 0、cmpxchg 为 0xf0）。 这里还顺带验证了返回值是 double —— Octave 会把 0xf0 这样的十六进制字面量解析成 uint8，所以打包时必须显式转换。

用例 14：汇编器解析标号
原始用例（asm labels are resolved） 
R = bpf.regs ();
a = bpf.Asm ();
a.mov64_imm (R.R0, 1);
a.jeq_imm (R.R0, 1, 'target');
a.mov64_imm (R.R0, 2);
a.label ('target');
a.exit ();
b = a.bytes ();
assert (size (b), [4, 8]);
assert (b(2, 3:4), uint8 ([1, 0]));       % skip one instruction
assert (a.count (), 4);

汇编器最核心的能力：先发射带占位偏移的跳转，遇到 label 时记下当前槽位， 最后在 bytes() 里回填。这段程序是 r0=1; if (r0==1) goto skip; r0=2; skip: exit，共 4 条指令， 跳转偏移应当是 1（跳过一条指令），count() 也应当是 4。

用例 15：未定义的标号会被报告
原始用例（undefined labels are reported） 
a = bpf.Asm ();
a.jeq_imm (0, 0, 'nowhere');
fail ('a.bytes ()', 'undefined label');

引用了不存在的标号必须在生成时明确报错，否则得到的是一段跳到随机位置的程序。 fail() 断言错误信息里包含 undefined label。

用例 16：记录 map 重定位
原始用例（map relocations are recorded） 
a = bpf.Asm ();
a.ld_map_fd (1, 'mymap');
a.exit ();
r = a.relocations ();
assert (numel (r), 1);
assert (r(1).slot, 0);
assert (r(1).sym, 'mymap');
assert (strcmp (r(1).kind, 'map_fd'));

ld_map_fd 除了写下两条指令，还要登记一条重定位： slot=0（第 0 个指令槽）、sym='mymap'、kind='map_fd'。 bpf.Elf 随后会用 slot*8 作为 r_offset， 指向符号表里的 map 符号，libbpf 由此知道该往哪个 imm 写 map fd。

tst_btf.m —— BTF 编码

验证 bpf.BtfBuilder 生成的 BTF 是否满足内核与 libbpf 的要求：类型大小、对齐、头字段、以及"生成 → 写文件 → 解析回来"的往返一致性。

用例 1：整数类型带有正确的字节数与位宽
原始用例（integer types carry the right size and bit width） 
B = bpf.BtfBuilder ();
i1 = B.add_int ('int', 4, bpf.BtfBuilder.ENC_SIGNED);
i8 = B.add_int ('unsigned long long', 8, 0);
assert (B.size_of (i1), 4);
assert (B.size_of (i8), 8);
assert (B.kind_of (i1), bpf.BtfBuilder.KIND_INT);
assert (B.name_of (i8), 'unsigned long long');

add_int 返回类型编号，size_of 给出字节数，kind_of 给出 BTF kind （INT=1），name_of 能按名字偏移把字符串取回来。 这条用例同时覆盖了字符串表的去重与"按偏移反查"两条路径。

用例 2：指针与数组
原始用例（pointers and arrays） 
B = bpf.BtfBuilder ();
i4 = B.add_int ('int', 4, 1);
p = B.add_ptr (i4);
a = B.add_array (i4, 4, i4);
assert (B.size_of (p), 8);
assert (B.size_of (a), 16);

指针在 BTF 里固定是 8 字节；数组的大小等于元素大小乘以元素个数（4×4=16）。 数组的 nelems 正是 libbpf 读取 __uint(type, ...) 这类 map 属性的地方， 所以这个数字不能出错。

用例 3：结构体按自然对齐排布
原始用例（structures are laid out with natural alignment） 
B = bpf.BtfBuilder ();
u8 = B.add_int ('unsigned char', 1, 0);
u64 = B.add_int ('unsigned long long', 8, 0);
members = struct ('name', {'a', 'b'}, 'type', {u8, u64});
s = B.add_struct ('thing', members);
assert (B.size_of (s), 16);

成员 {unsigned char a; unsigned long long b;} 按 C 的自然对齐排布： a 在偏移 0，b 对齐到 8，结构体总大小 16。 libbpf 依靠 BTF 成员的 bit offset 来定位 map 属性，偏移算错就会读出错的值。

用例 4：BTF 头与字符串表格式正确
原始用例（the header and the string table are well formed） 
B = bpf.BtfBuilder ();
B.add_int ('int', 4, 1);
b = B.bytes ();
assert (b(1), uint8 (0x9f));
assert (b(2), uint8 (0xeb));
assert (b(3), uint8 (1));            % version
assert (double (bpf.bytes2num (b(5:8))), 24);  % hdr_len
assert (double (bpf.bytes2num (b(9:12))), 0);  % type_off
type_len = double (bpf.bytes2num (b(13:16)));
str_off = double (bpf.bytes2num (b(17:20)));
str_len = double (bpf.bytes2num (b(21:24)));
assert (str_off, type_len);
assert (numel (b), 24 + type_len + str_len);

直接检查 BTF 头的字节：魔数 0xeb9f 以小端存放（0x9f 0xeb）、version=1、 hdr_len=24、type_off=0、str_off 紧接在类型段之后、总长度等于 24 + type_len + str_len。 头写错的话内核在 BPF_BTF_LOAD 时会直接返回 EINVAL，而且往往连日志都不给。

用例 5：生成的对象 BTF 能被解析器读回
原始用例（an object BTF round trips through the parser） 
if (bpf.have_bpf ())
  b = bpf.Builder ('GPL');
  b.map ('counts', 'array', 'u32', 'u64', 8);
  f = tempname ();
  fid = fopen (f, 'wb'); fwrite (fid, b.elf (), 'uint8'); fclose (fid);
  B = bpf.BTF.from_file (f);
  unlink (f);
  assert (B.type_cnt () > 0);
  id = B.find_by_name_kind ('counts', bpf.BTF.KIND_VAR);
  assert (id > 0);
endif

端到端自洽性测试：用 Builder 生成一个带 array map 的 ELF 镜像，写入临时文件， 再用 libbpf 的 btf__parse_elf() 解析回来，确认能找到名为 counts 的 VAR 类型。 若当前环境没有 eBPF 权限，整个用例会被跳过。

tst_elf.m —— ELF 目标文件生成

验证 bpf.Elf 产生的镜像在结构上是合法的 eBPF 目标文件，并且重定位、license、可复现性这些关键性质都成立。

用例 1：ELF 头标识出 64 位小端 BPF 对象
原始用例（the ELF header identifies a 64 bit little endian BPF object） 
b = bpf.Builder ('GPL');
p = b.program ('kprobe/do_sys_openat2', 'hello');
p.mov64_imm (0, 0);
p.exit ();
img = b.elf ();
assert (img(1:4), uint8 ([0x7f, double('E'), double('L'), double('F')]));
assert (img(5), uint8 (2));                        % ELFCLASS64
assert (img(6), uint8 (1));                        % ELFDATA2LSB
assert (double (bpf.bytes2num (img(17:18))), 1);    % ET_REL
assert (double (bpf.bytes2num (img(19:20))), 247);  % EM_BPF

检查 ELF 魔数 0x7f 'E' 'L' 'F'、ELFCLASS64=2、ELFDATA2LSB=1、 e_type=ET_REL=1、e_machine=EM_BPF=247。 这几个字段错任何一个，libbpf 都会以 "not a valid eBPF object file" 拒绝加载。

用例 2：每个生成的对象都带 license 段
原始用例（every generated object has a license section） 
b = bpf.Builder ('GPL');
p = b.program ('kprobe/x', 'x');
p.exit ();
img = b.elf ();
assert (numel (img) > 64);

即使程序只有一条 exit，也必须生成 license 段——libbpf 强制要求， 缺少时报 "missing license"。用例用镜像长度大于 64 字节（ELF 头长度） 来粗略确认其它段确实被写了出来。

用例 3：引用 map 会产生重定位
原始用例（a map reference produces a relocation） 
b = bpf.Builder ('GPL');
b.map ('m', 'array', 'u32', 'u64', 4);
p = b.program ('kprobe/x', 'x');
p.ld_map_fd (1, 'm');
p.exit ();
img = b.elf ();
assert (numel (img) > 256);
r = p.relocations ();
assert (numel (r), 1);

引用 map 时必须生成 .rel<section> 段并登记一条重定位， 否则 libbpf 找不到 map fd，程序里会残留 imm=0 的伪指令，加载后立刻崩。 用例断言镜像确实变大，且 relocations() 恰好返回一条记录。

用例 4：license 字符串出现在镜像里
原始用例（the license string ends up in the image） 
b = bpf.Builder ('Dual BSD/GPL');
p = b.program ('kprobe/x', 'x');
p.exit ();
img = b.elf ();
txt = char (img);
assert (! isempty (strfind (txt, 'Dual BSD/GPL')));

自定义的 license（这里是 Dual BSD/GPL）必须原样出现在镜像中， 因为内核用它判断该程序是否允许调用 GPL-only 的 helper。

用例 5：引用不存在的 map 会报错
原始用例（referencing an unknown map is an error） 
b = bpf.Builder ('GPL');
p = b.program ('kprobe/x', 'x');
p.ld_map_fd (1, 'nosuchmap');
p.exit ();
fail ('b.elf ()', 'unknown map');

如果程序引用了 Builder 里没有声明过的 map，必须立刻报错， 而不是生成一个"要到加载时才失败"的镜像。错误信息里包含 unknown map。

用例 6：同一个 Builder 生成的镜像稳定可复现
原始用例（the same builder produces a stable image） 
b = bpf.Builder ('GPL');
b.map ('m', 'array', 'u32', 'u64', 4);
p = b.program ('kprobe/x', 'x');
p.ld_map_fd (1, 'm'); p.exit ();
assert (b.elf (), b.elf ());

同一个 Builder 连续两次 elf() 必须得到完全相同的字节。 这说明生成过程没有隐藏状态（例如不稳定的哈希遍历顺序、时间戳等）， 也让"同样的源码生成同样的对象"成为可验证的性质。

tst_map.m —— eBPF map 操作

真正与内核交互的一组用例：创建 map、读写元素、遍历、删除、回读内核信息。没有 eBPF 权限时会整体跳过。

用例 1：array map 的值可以原样往返
原始用例（array maps round trip values） 
if (bpf.have_bpf ())
  m = bpf.Map.create ('array', 4, 8, 4, 'octave_tst_array');
  assert (m.key_size (), 4);
  assert (m.value_size (), 8);
  assert (m.max_entries (), 4);
  for k = 0:3
    m.update (k, 1000 + k);
  end
  assert (m.lookup (2), uint64 (1002));
  clear m
endif

创建 array map（key 4 字节、value 8 字节、4 个条目），写入 0..3，再读回第 2 个。 既验证了 Map.create 的参数确实传给了内核（key_size / value_size / max_entries）， 也验证了 8 字节的值会被还原成 uint64 而不是一串裸字节。

用例 2：hash map 支持删除与遍历
原始用例（hash maps support removal and iteration） 
if (bpf.have_bpf ())
  m = bpf.Map.create ('hash', 4, 8, 8, 'octave_tst_hash');
  m.update (7, 42);
  assert (m.lookup (7), uint64 (42));
  assert (m.next_key (), uint32 (7));
  m.remove (7);
  assert (isempty (m.next_key ()));
  clear m
endif

hash map 支持删除与遍历（array map 不支持删除）。写入 key=7 之后， 从"空 key"开始调用 next_key() 枚举得到 7；删除后再枚举应当返回空。 这条用例覆盖了 BPF_MAP_GET_NEXT_KEY 的两种调用方式与 ENOENT 的处理。

用例 3：原始字节访问
原始用例（raw byte access） 
if (bpf.have_bpf ())
  m = bpf.Map.create ('array', 4, 8, 1, 'octave_tst_raw');
  m.update (0, uint8 (1:8));
  assert (m.lookup (0, 'raw'), uint8 (1:8));
  clear m
endif

用 uint8(1:8) 直接写 8 字节 value，再以 'raw' 模式读回完全相同的字节。 这条保证二进制数据在往返过程中不会被数值转换破坏——对于存放结构体或 网络包内容的 map，这是必须的。

用例 4：内核把 map 信息报告回来
原始用例（the kernel reports the map back） 
if (bpf.have_bpf ())
  m = bpf.Map.create ('array', 4, 4, 3, 'octave_tst_info');
  i = m.info ();
  assert (i.type, bpf.map_type ('array'));
  assert (i.max_entries, 3);
  assert (strcmp (i.name, 'octave_tst_info'));
  clear m
endif

BPF_OBJ_GET_INFO_BY_FD 把内核真正创建出来的 map 信息读回 Octave： 类型、max_entries、名字。它证明前面的参数确实到达了内核， 而不只是在用户态记录了一份"我以为创建了什么"的副本。

用例 5：字节转换助手
原始用例（byte conversion helpers） 
assert (bpf.num2bytes (1, 4), uint8 ([1 0 0 0]));
assert (bpf.num2bytes (uint32 (258), 4), uint8 ([2 1 0 0]));
assert (bpf.bytes2num (uint8 ([2 1 0 0])), uint32 (258));
assert (double (bpf.bytes2num (uint8 ([2 1 0 0]))), 258);
assert (bpf.bytes2num (uint8 ([0xff 0xff 0xff 0xff]), true), int32 (-1));
assert (bpf.bytes2num (uint8 ([])), []);

字节序与符号处理：num2bytes(1,4) 得到 [1 0 0 0]（小端）、 258 得到 [2 1 0 0]、反向还原为 uint32(258)、 int32 补码还原为 -1、空输入返回空。 这两个助手是 map 读写与 BTF/ELF 编码的共同基础。

tst_object.m —— 对象加载与运行

把前面所有环节串起来的集成测试：编写程序、生成镜像、加载、运行、读取结果，以及错误路径（非法指令、非法镜像）的表现。

用例 1：XDP 程序加载并通过 BPF_PROG_TEST_RUN 运行
原始用例（an XDP program loads and runs through BPF_PROG_TEST_RUN） 
if (bpf.have_bpf ())
  R = bpf.regs ();
  b = bpf.Builder ('GPL');
  b.map ('hits', 'array', 'u32', 'u64', 1);
  p = b.program ('xdp', 'counter');
  p.st_w (R.R10, -4, 0);
  p.ld_map_fd (R.R1, 'hits');
  p.mov64_reg (R.R2, R.R10);
  p.add64_imm (R.R2, -4);
  p.call (bpf.helper ('map_lookup_elem'));
  p.jeq_imm (R.R0, 0, 'done');
  p.mov64_imm (R.R1, 1);
  p.atomic_dw (R.R0, R.R1, 0, bpf.atomic_op ('add'));
  p.label ('done');
  p.mov64_imm (R.R0, 2);
  p.exit ();

  obj = b.build ();
  obj.load ();
  prog = obj.find_program ('counter');
  r = prog.test_run (uint8 (zeros (1, 100)));
  assert (r.retval, 2);
  assert (obj.find_map ('hits').lookup (0), uint64 (1));
  clear obj
endif

整套流程的集成测试：用 Octave 写一个 XDP 程序（把 map 里的计数加 1，然后返回 XDP_PASS=2）， 生成 ELF、加载，再用 BPF_PROG_TEST_RUN 从用户态喂进一个 100 字节的包， 断言返回值是 2、且 map 里的计数变成了 1。 这是"用 Octave 写 eBPF 程序"最直接的证明：指令、BTF、ELF、加载、运行全部由 Octave 完成。

用例 2：被拒绝的程序会给出校验器日志
原始用例（a rejected program reports the verifier log） 
if (bpf.have_bpf ())
  b = bpf.Builder ('GPL');
  p = b.program ('xdp', 'bad');
  p.ldx_dw (0, 1, 0);         % 8 byte load from an XDP context: invalid
  p.exit ();
  obj = b.build ();
  obj.set_log (65536);
  failed = false;
  try
    obj.load ();
  catch
    failed = true;
  end
  assert (failed);
  clear obj
endif

故意写一条非法指令（对 XDP 上下文做 8 字节加载），确认加载失败会抛出异常而不是静默成功。 加载之前已经用 obj.set_log() 挂上了日志缓冲区， 所以 obj.get_log('bad') 能拿到内核校验器的完整输出， 这正是排查"程序为什么加载不了"的标准手段。

用例 3：对象元信息可见
原始用例（object metadata is exposed） 
if (bpf.have_bpf ())
  b = bpf.Builder ('GPL');
  b.map ('m', 'array', 'u32', 'u64', 2);
  p = b.program ('xdp', 'x');
  p.mov64_imm (0, 2);
  p.exit ();
  obj = b.build ();
  assert (numel (obj.program_names ()), 1);
  assert (strcmp (obj.program_names (){1}, 'x'));
  assert (strcmp (obj.map_names (){1}, 'm'));
  clear obj
endif

加载后能正确枚举对象内部的程序名与 map 名（program_names / map_names），这是后续 find_program / find_map 以及 attach_all 的基础。

用例 4：无效的内存镜像会被拒绝
原始用例（an invalid in-memory image is rejected） 
fail ('bpf.Object.from_mem (uint8 (1:32), ''junk'')', 'libbpf');

把 32 个随机字节当作 ELF 传进 bpf.Object.from_mem，必须报错， 且错误信息以 libbpf: 开头。 这条覆盖了错误路径，确保无效输入不会让进程崩溃。

用例 5：Builder 的元信息
原始用例（builder metadata） 
b = bpf.Builder ('GPL');
b.map ('a', 'array', 'u32', 'u64', 1);
b.map ('b', 'hash', 'u32', 'u32', 4);
assert (b.map_names (), {'a', 'b'});
m = b.find_map ('b');
assert (strcmp (m.type_name, 'BPF_MAP_TYPE_HASH'));
assert (m.max_entries, 4);

不生成镜像也能查询 Builder 的内容：map_names 的顺序与声明顺序一致 （{'a','b'}），find_map 能取回类型名与 max_entries。 这一部分完全在用户态运行，不需要任何特权。

tst_misc.m —— 环境、枚举与工具

版本、命令表、枚举查询、寄存器表、helper 表、日志捕获与 CPU 数量等外围但每天都在用的接口。

用例 1：报告 libbpf 版本
原始用例（libbpf version is reported） 
v = bpf.version ();
assert (v.major, 1);
assert (v.minor >= 0);
assert (ischar (v.string));

bpf.version() 返回 major / minor / string。 断言 major == 1 是因为 libbpf 1.x 的公开 ABI 稳定；minor 只要求 >= 0， 这样同一个包既能跑在 1.6 上，也能跑在更新的共享库上。

用例 2：命令表完整且有序
原始用例（the command list is complete and sorted） 
c = bpf.commands ();
assert (iscellstr (c));
assert (numel (c) > 100);
assert (strcmp (c{1}, sort (c){1}));
assert (any (strcmp (c, 'object_load')));

bpf.commands() 必须返回排序过的 cellstr，数量大于 100（当前 182）， 并且包含 object_load 这样的关键命令。 它同时充当"oct 文件是否成功加载、命令表是否完整"的哨兵用例。

用例 3：指针与返回值的约定
原始用例（pointer conventions） 
assert (isstruct (bpf.raw ('version')));

bpf.raw 是所有底层命令的统一入口， 这里用 version 验证"调用 → 返回 Octave 结构体"这条通路工作正常。

用例 4：枚举查询同时接受名字与编号
原始用例（enumeration lookups accept names and numbers） 
assert (bpf.map_type (2), 2);
[v, n] = bpf.map_type (2);
assert (v, 2);
assert (strcmp (n, 'BPF_MAP_TYPE_ARRAY'));
assert (bpf.map_type ('ringbuf'), 27);
assert (bpf.prog_type ('xdp'), 6);
assert (bpf.link_type ('tracing') > 0);
fail ('bpf.map_type (''not_a_map_type'')', 'unknown bpf_map_type name');

编号与名字都能查询，名字可长可短；第二个输出给出规范名； 不存在的名字必须报错（信息形如 unknown bpf_map_type name ...）。 另外注意这里把名字放在第二个输出而不是结构体字段里， 是因为 Octave 无法解析 bpf.map_type(x).field 这种"包函数调用后紧跟字段"的写法。

用例 5：寄存器表
原始用例（register table） 
R = bpf.regs ();
assert (R.R0, 0);
assert (R.R10, 10);
assert (R.FP, 10);

bpf.regs() 给出 r0…r10，并额外提供 FP=10（帧指针）与 RET=0（返回值寄存器） 两个别名，让汇编代码更接近内核文档里的写法。

用例 6：helper 表完整
原始用例（helper table completeness） 
assert (numel (fieldnames (bpf.helper_table ())) > 200);
assert (bpf.helper (1), 1);

helper 表由 libbpf 的 bpf_helper_defs.h 生成，断言字段数大于 200（当前 211）。 将来升级 libbpf 头文件时，这条用例会提醒重新生成表格。

用例 7：日志捕获可以打开与清空
原始用例（log capture can be enabled and cleared） 
bpf.capture (true);
bpf.get_log ('clear');
assert (ischar (bpf.get_log ()));

捕获开关与清空操作都能正常工作，清空之后 bpf.get_log() 仍然返回字符串（可能为空）。 调试加载失败时依赖这条通路，所以它本身也要有测试。

用例 8：CPU 数量
原始用例（number of cpus） 
assert (bpf.num_cpus () >= 1);

bpf.num_cpus() 返回 possible CPU 数量，per-CPU map 需要用它来分配 value 空间， 因此必须大于等于 1。
